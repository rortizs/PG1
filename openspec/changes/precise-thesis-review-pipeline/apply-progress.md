## Deviations From Design

- **`ExtractedSection.parent_index` (index-based) instead of a literal `parent_section_id` field.** `design.md` D2's mapping paragraph says section detection produces "`parent_section_id` via the level stack" — read literally as a Python dataclass field name, this is impossible: no real database id exists yet at extraction time (ids are only assigned once `insertDocumentSections` runs, on the Node side). Design's own D3 contract for `insertDocumentSections` confirms the intended shape is index-based (`sections[] ... { index, parentIndex|null, ... }`, resolved against `idByIndex` "safely because a parent heading ALWAYS precedes its child in document order"). So D2's `parent_section_id` wording describes the eventual DB **column** the level-stack value maps to, not a literal Python field name — implemented as `ExtractedSection.parent_index: int | None`, matching D3's own `parentIndex` contract exactly, and documented with an explicit docstring on the dataclass explaining why. This is an implementation-necessary interpretation, not a behavioral deviation — the end result (a real `document_section.parent_section_id` FK, correctly resolved) is exactly what D2/D3 together specify.
- **`documentSectionId` resolved by page-range containment, not `f.section_index`.** Design.md D3's literal wiring formula is `documentPageId/documentSectionId ... from idByPageNumber[f.page_number] and idByIndex[f.section_index]` — but `f.section_index` is a field on the **chunked** review response contract (design.md's Interfaces/Contracts `/internal/review` response, `{"findings": [{..., "section_index": 0}]}`), which is PR5's scope (Work Unit 8), not PR1's. The current, still-single-call `cag_review.py`/`/internal/review` response this pass leaves untouched only reports `page_number`/`section_title` per the orchestrator's explicit instruction ("this pass does not change how many findings are produced yet... `test_cag_review.py`'s existing single-finding assertions must stay green"). Implemented `findSectionIdForPage()` instead: given the real inserted sections' `[startPageNumber, endPageNumber]` ranges, picks the most specific (smallest-span) section containing the finding's `page_number`. This is a forward-compatible, in-scope way to satisfy "wire real FK ids... before persisting any finding" using data that genuinely exists in PR1 — PR5 can later switch to the more precise `section_index`-based lookup once the chunked contract carries it, without changing `insertDocumentSections`/`insertDocumentPages` at all.
- **`main.py` untouched** (see the dedicated discovery note above) — a structural consequence of `ExtractionResult.to_dict()` already flowing through the existing route unchanged, not a deviation from the requirement itself (verified directly by an endpoint-level test).
