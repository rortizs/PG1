### Work Unit 7 — Finding/Evidence Persistence + Inline Queue

**`apps/api/src/db/review-repository.mjs`** (new): real `pg`-backed writes, reusing `migrate.mjs`'s `withClient` helper (now exported — this is the REFACTOR explicitly deferred from Work Unit 2 in PR A, now completed). `seedNormativeSources()` is idempotent (SELECT-by-title before INSERT; seeding twice returns the same 4 IDs, verified). `persistFinding()` is the evidence-before-finding guarantee: it validates `evidence` is non-empty and every snippet has real text *before opening a transaction*; inside the transaction it inserts `evidence_snippet` row(s) first, then `finding`, then the `finding_evidence` join rows, `COMMIT`s only at the end, and `ROLLBACK`s on any failure (including the DB's own `evidence_snippet_location_check` constraint if a snippet has neither a page/section nor an uncertainty flag). Calling it with zero evidence throws `EvidenceRequiredError` **before any row is written** — verified directly against live Postgres (`review-repository.test.mjs`'s second test: `finding` count stays `0` after the rejected call).

**Gotcha found and fixed**: `pg` returns `BIGINT` columns (every id in this schema is `GENERATED ALWAYS AS IDENTITY`, i.e. `bigint`) as JS strings, not numbers, because a JS `number` cannot safely represent the full `int8` range. The repository's first draft returned raw string ids, which failed `Number.isInteger()` assertions in the live test. Fixed with a small `toId()` coercion helper applied to every `RETURNING id` read — safe here since ids never approach `Number.MAX_SAFE_INTEGER` in practice, but worth flagging for anyone adding new repository queries later.

**`apps/api/src/jobs/inline-review-queue.mjs`** (new): `createInlineReviewQueue({ processor })` — the exact same `add(name, payload, options)` call signature and returned job shape (`{id, name, payload, idempotencyKey, attempts}`) as the pre-existing `createMemoryReviewQueue` in `review-queue.mjs`, plus the same idempotency-by-key behavior and a `jobs()` accessor. The only behavioral difference: `add()` `await`s the given `processor(payload)` **before** resolving, so by the time the caller's `await queue.add(...)` returns, the work is already done — this is the literal mechanism behind the spec's "Synchronous Review-Run Trigger" requirement. `review-queue.mjs` and `review-run-lifecycle.mjs` are **byte-for-byte untouched** (zero diff) — verified via `git diff`.

**`apps/api/src/jobs/review-orchestrator.mjs`** (new): `createReviewOrchestrationProcessor()` builds the actual extract → segment → validate → rag_review → report → complete pipeline (calling `lifecycle.transitionReviewRun()` through the real, valid state machine from `review-run-lifecycle.mjs` — no shortcuts, every intermediate status is genuinely visited) around injectable `extractThesisText`/`runCagReview`/`resolveNormativeSourceId`/`resolveThesisDocumentDbId` functions. It never rethrows: any failure (worker unreachable, malformed CAG response, thrown error) is caught, recorded on the `review_run` row (`error_summary`, `failed_at`) via `repository.updateReviewRunStatus`, and reported through `lifecycle.markJobFailed()` — so `inline-review-queue.mjs`'s `add()` always resolves and the triggering request never hangs or throws past the queue seam. `createReviewPipeline()` wires a full real instance (`review-run-lifecycle.mjs` + `inline-review-queue.mjs` + this processor) via a small lazy-binding proxy (needed because the lifecycle needs the queue and the queue's processor needs to call back into the lifecycle — resolved with a proxy object assigned after both are constructed). `defaultRunCagReview()` is a real, production-shaped `fetch()` call to `${WORKER_BASE_URL}/internal/review` with a 30s timeout, matching design.md's documented `/internal/review` JSON contract exactly (snake_case fields consumed as-is, no needless camelCase remapping layer).

### Deliberate Scope Boundary — Live HTTP Wiring Deferred (flagging per design-vs-constraint conflict)

**This is the one place in PR C where I deviated from a literal reading of `design.md`, and I'm flagging it explicitly rather than silently deciding either way.**

`design.md`'s data-flow diagram and decision #10 depict `reviewRunLifecycle.startReviewRun` calling `inlineQueue.processor` as *the* production wiring — implying `api-contract.mjs`'s live `handleApiRequest` (used by both NestJS controllers over real HTTP *and* by `contract.test.mjs`'s direct pure-handler assertions) should use the inline queue. I traced this concretely and found a hard conflict with this pass's explicit instruction to preserve the 40 pre-existing `apps/api` tests' tested behavior:

- `contract.test.mjs`'s `"POST .../review-runs returns lifecycle-backed 202 response"` test asserts `response.body.status === "queued"` for a **fabricated, never-uploaded** document id (`doc_contract`) — a "seam contract" check per design decision #1's own rationale ("preserve the pure-handler seam"), not an end-to-end behavioral check.
- `accepted(run, idempotencyKey)` inside `review-run-lifecycle.mjs`'s `startReviewRun` reads `run`'s **current** status *after* `await queue.add(...)` resolves (it clones the same, mutated-by-reference `run` object). If `api-contract.mjs`'s shared singleton used the inline queue, **any** synchronous processing — success or failure — would flip `run.status` away from `"queued"` before that assertion runs, breaking it. There is no way to satisfy both "the shared handler is genuinely synchronous" and "this specific test's `status: "queued"` assertion is untouched" without either changing that test (out of the explicitly protected set) or using a separate handler instance for live traffic.

Given the explicit instruction "do not delete those files or change their tested public behavior for the 40 apps/api tests that already pass" takes precedence, I built the **entire persistence + inline-queue + orchestration mechanism as real, fully tested, standalone modules** (proven against live Postgres via `review-repository.test.mjs` and `review-orchestrator.test.mjs`, driving the actual unmodified `review-run-lifecycle.mjs`) but **did not** rewire `api-contract.mjs`'s module-level singleton or the two NestJS controllers to use them for live HTTP traffic. `createReviewPipeline()` in `review-orchestrator.mjs` is the ready-to-use factory a follow-up step would plug into `main.ts`/a live-aware handler — the mechanism is real and tested, just not yet the thing controllers call. This matches `tasks.md`'s own Work Unit 7 rollback boundary ("lifecycle stays on in-memory Map"), which implies the Map-backed path remaining the active default was already an accepted state, not solely a rollback fallback.

**Practical consequence**: a real `curl` through the live NestJS server's `POST /api/v1/thesis-documents/{id}/review-runs` route still returns the same in-memory-only 202 response as before this pass (no live persistence yet on that exact HTTP path). The full real pipeline is proven correct and reusable, exercised directly (not through HTTP) in the new integration tests. Wiring it into the live request path is a small, well-scoped follow-up (swap `api-contract.mjs`'s handler for a `createReviewPipeline()`-backed live instance, likely alongside `contract.test.mjs` being explicitly rescoped to test the pure stub path only) — explicitly recommended as the next step before PR D's results-page work can show anything beyond its placeholder empty state with a real backend.

**Status as of PR D: this deviation is now closed.** See "PR D — Live HTTP Wiring" below for the resolution actually shipped (a real-vs-stub routing split, not a `contract.test.mjs` rescoping) and why that approach was chosen over the one sketched above.

### Live HTTP Wiring (the closed PR C deviation)

**Problem investigated**: `contract.test.mjs`'s `"POST .../review-runs returns lifecycle-backed 202 response"` test asserts `status: "queued"` for a **fabricated, never-uploaded** document id (`doc_contract`). Driving every document id through the real, synchronous `createReviewPipeline()` would break that assertion, because ANY synchronous processing on the shared handler — success or failure — flips the run's status away from `"queued"` before the response is read (the run object is mutated in place inside `review-run-lifecycle.mjs`'s Map, and `accepted()` reads its *current* status after `await queue.add(...)` resolves).

**Resolution chosen (real-vs-stub routing split, not a `contract.test.mjs` rescope)**: only document ids that were genuinely persisted through a real `POST /api/v1/thesis-documents` upload — **with `DATABASE_URL` configured** — are routed through the real pipeline. Any other document id (fabricated ids, or real uploads made while `DATABASE_URL` is unset) keeps using the pre-existing in-memory stub `review-run-lifecycle.mjs` singleton, byte-for-byte the same code path as before this pass. This required **zero changes to `contract.test.mjs`'s protected assertion** — a stronger outcome than the rescoping option sketched in PR C's own notes, and the one actually implemented.

New module `apps/api/src/live-review-pipeline.mjs` is the composition root:
- **`documentStorage`**: a process-wide singleton using the new `createFilesystemObjectStorage` adapter (design decision #11, deferred from PR C) — real bytes on disk under `os.tmpdir()/pg1-thesis-storage` by default. This also fixes a **real, pre-existing bug**: `api-contract.mjs` previously called `processThesisDocumentUpload` with no `storage` argument, so `upload-service.mjs`'s default parameter (`storage = createMemoryObjectStorage()`) created a **brand-new, empty in-memory store on every single request** — uploaded bytes were silently discarded the instant the upload response was sent, even before this pass's live-pipeline work. A subsequent review-run trigger could never have read them back, regardless of any other wiring.
- **`uploadedDocuments`**: an in-process registry (external doc id -> `{dbId, sha256, storageKey, contentType, filename}`), populated ONLY when `registerUploadedDocument()` successfully inserts a real `thesis_document` row. `isKnownUploadedDocument(id)` is exactly this registry's membership check — which is what makes the real-vs-stub split correct and safe: an id can only ever reach the real pipeline if it was genuinely, durably persisted first.
- **`getLivePipeline()`**: lazily builds (and caches) a `createReviewPipeline()` instance, wiring `resolveThesisDocumentDbId` (registry lookup), `extractThesisText` (reads bytes back from `documentStorage`, POSTs a real `multipart/form-data` request via Node's native `fetch`+`FormData`+`Blob` to the worker's `/internal/extract`), and `resolveNormativeSourceId` (cached `repository.seedNormativeSources()` lookup by corpus filename). Returns `null` when `DATABASE_URL` is unset — the process then behaves exactly as it did before this pass.

`api-contract.mjs` changes:
- `handleApiRequest` is now `async function` (previously a plain function that happened to return a promise only on one branch) — required because real DB reads for GET routes are inherently async. **All 7 non-awaited `handleApiRequest(...)` call sites in `contract.test.mjs` were updated to `await`** — a purely mechanical, non-assertion-changing accommodation (see "Deviations" below for why this is a legitimate, documented evolution and not a silent behavior change).
- POST `/thesis-documents`: uses the shared `documentStorage` singleton (fixing the bug above) and, on a `201`, calls `registerUploadedDocument()`. Only a genuine Postgres **connection-level** failure (checked via error code: `ECONNREFUSED`/`ENOTFOUND`/`ETIMEDOUT`/`08000`/`08003`/`08006`/`57P03`) turns the response into a `503` (spec: "Postgres unreachable -> 5xx"). Any other DB error (e.g. schema not yet migrated in a given environment) is logged via `console.error` and degrades to a successful `201` without live-pipeline eligibility — **this was a real bug found and fixed during TRIANGULATE** (see below).
- POST `/thesis-documents/{id}/review-runs`: routes to `getLivePipeline().lifecycle` for a known/persisted document, else the existing stub `reviewRunLifecycle` — wrapped in a `try/catch` returning `503` on an unexpected throw (defensive; the orchestrator's own internal catch-all means this should not normally fire).
- GET `/review-runs/{id}`: tries the live lifecycle's `getReviewRun` first, then the stub lifecycle's, and only falls back to the fully fabricated `reviewRunStatus()` stub if the run id is unknown to both — **exactly** preserving `contract.test.mjs`'s `run_contract` (never created anywhere) test case. Real responses get an honest computed `summary.findings` count (via a new `review-repository.mjs` query, only queried once the run is `completed`).
- GET `/review-runs/{id}/findings`: reads real persisted findings via the new `repository.listFindingsForReviewRun(reviewRunDbId)` when the run belongs to the live pipeline, else `[]` (unchanged stub behavior).

`review-orchestrator.mjs`: `createReviewPipeline()` now also returns `repository` and `getReviewRunDbId(lifecycleRunId)` (backed by a small property attached to the internal `process` function — `process.reviewRunDbIdByLifecycleId` — so `inline-review-queue.mjs`'s plain-callable-function contract for `processor` is unchanged). This is what lets the live HTTP GET findings/summary paths map an external run id back to the internal Postgres `review_run.id`.

### A Real Bug Found During TRIANGULATE (and fixed)

Running the full `apps/api` suite with `DATABASE_URL` set (to verify the new live wiring against real Postgres) initially **broke two pre-existing, previously-green tests**:

1. `review-repository.test.mjs`'s existing test: my new `listFindingsForReviewRun` query returned `page_number` as a `pg`-BIGINT string (`'3'`) instead of a number — the exact same class of bug documented in PR C's Issues Found, just in a new query I forgot to coerce. Fixed with the existing `toId()` helper.
2. `upload-storage.test.mjs`'s `"API contract delegates upload validation when file input is provided"` test started failing with a `503` when the *whole* suite ran with `DATABASE_URL` set (`node --test`'s `--test-concurrency=1` still runs each **file** as its own process, sequentially, against the SAME live Postgres instance). Root cause: several *other* integration test files (`review-repository.test.mjs`, `review-orchestrator.test.mjs`, `live-review-integration.test.mjs`) each bracket their own `migrateDown`/`migrateUp`/`migrateDown` and leave the schema **dropped** when they finish. By the time `upload-storage.test.mjs` runs (alphabetically last), the schema was gone, so my new `registerUploadedDocument()` call inside the upload path hit `relation "thesis_document" does not exist` and (in its first draft) turned an otherwise-successful upload into a `503`.

   This exposed a real design flaw: making a previously DB-agnostic, contract-shape-only test implicitly DB-schema-dependent whenever `DATABASE_URL` happens to be set in the environment. Fixed by classifying the DB error: only genuine **connection-level** failures (Postgres unreachable) turn the upload response into a `5xx`; any other DB error (like a missing table from unrelated test-file cleanup) is logged and degrades to a successful upload without live-pipeline eligibility for that document. This preserves PR C's own established invariant — "`DATABASE_URL=... pnpm test` passes the whole suite cleanly" (its own evidence: "50 pass / 0 fail") — which is now **51 pass / 0 fail** with this pass's one added test file.

However, live verification on this specific development machine required a temporary port remap to `5433:5432` because a pre-existing, project-unrelated Homebrew `postgresql@17` server already occupies `127.0.0.1:5432`/`[::1]:5432` locally (discovered this session, not caused by this change). This is documented as a machine-specific environment risk below, not a design change.
- No other deviations. `migrate.mjs`'s API shape (`splitMigration`, `migrateUp`, `migrateDown`, CLI `up|down`) matches design decision #7 (`pg` client splitting `-- UP`/`-- DOWN`) exactly.
- The "REFACTOR: share pg client factory with review-repository.mjs" sub-task from `tasks.md` Work Unit 2 is explicitly deferred to Work Unit 7 (PR C), since `review-repository.mjs` does not exist yet in this pass — creating it now would be out of scope for PR A.

## Issues Found

- **Local port 5432 conflict (environment-specific, not a code defect)**: on this machine, a pre-existing Homebrew `postgresql@17` service binds `127.0.0.1:5432` independently of Docker, which intercepts `localhost:5432` connections ahead of Docker's own `0.0.0.0:5432` port-forward. Anyone reproducing this locally with a system Postgres already running on 5432 will see `role "pg1" does not exist` (they're hitting the wrong server) rather than a Docker/compose failure. Documented in Test Commands Run and Risks; no code change needed — this is purely a local-environment note for future contributors and does not affect the canonical `docker-compose.yml`/`DATABASE_URL` contract shipped in this PR.
- **PR B — real-HTTP 404 shape gap (known, not fixed in this pass)**: unmatched routes hit over real HTTP (e.g. `GET /api/v1/unknown`) now return Nest's default Express-style 404 JSON (`{"message":"Cannot GET ...","error":"Not Found","statusCode":404}`) instead of the pure handler's standard error shape (`{error, message, details, request_id, timestamp}`) used by `contract.test.mjs`'s "unsupported routes return the standard error shape" test. That test still passes because it calls `handleApiRequest` directly (unaffected). No spec scenario or `tasks.md` acceptance criterion in Work Unit 3 requires the real-HTTP 404 shape to match, so this was left as-is rather than adding an unscoped catch-all exception filter; flagging it here so a future PR can add a global Nest exception filter mapping unmatched routes to the standard error shape if that's desired.
- **PR B — pnpm build-script approvals required environment config**: this pnpm setup did not accept interactive `pnpm approve-builds` input in this tool environment; explicit `allowBuilds`/`onlyBuiltDependencies` entries were added to `pnpm-workspace.yaml` instead (for `esbuild`, `@parcel/watcher`, `lmdb`, `msgpackr-extract`). This is a one-time, environment-level, non-security-sensitive config change (all four are well-known dev-tooling native modules: esbuild's own binary downloader, Angular CLI's file watcher, and its dev-server cache backend) — not a per-PR concern, but noted for the next contributor who runs `pnpm install` fresh.
- **PR C — `pg` returns BIGINT columns as JS strings, not numbers**: every id in the schema is `BIGINT GENERATED ALWAYS AS IDENTITY`; `review-repository.mjs`'s first draft returned these raw (e.g. `"1"` instead of `1`), failing a live-pg integration test's `Number.isInteger()` assertion. Fixed with a small `toId()` coercion helper applied everywhere a `RETURNING id`/id column is read (both in the repository and, for its own raw verification queries, in the test file itself). Safe given this schema's actual id scale, but worth flagging for anyone adding new BIGINT-returning queries later — `pg` does not auto-coerce int8 by default.
- **PR C — concurrent live-pg integration test files raced each other**: `node --test tests/*.test.mjs` runs test files as concurrent subprocesses by default. Once 3 files (`migrate-runner`, `review-repository`, `review-orchestrator`) independently `migrateDown`/`migrateUp` against the SAME live Postgres database, they collided (`duplicate key value violates unique constraint "pg_extension_name_index"`, `relation "thesis_document" already exists`) when a real Postgres was actually running. This never manifested before because only one such file existed pre-PR-C. Fixed by adding `--test-concurrency=1` to `apps/api/package.json`'s `test` script — serializes file execution (no behavioral change to any individual test, only execution ordering; the full offline suite still completes in ~1.3s). This does not affect the normal `pnpm test` path when Postgres is unreachable (all live-pg tests skip immediately regardless of concurrency), only the opt-in live-verification scenario.
- **PR D — `pg` BIGINT-as-string bug, again, in a new query**: `listFindingsForReviewRun`'s `page_number` column (BIGINT) came back as a string, failing a new integration-test assertion. Same root cause and fix pattern as PR C's Issues Found entry (`toId()` coercion) — flagging again since this is the second time this exact class of bug has been caught, suggesting any FUTURE new query reading a BIGINT column should apply `toId()` from the start rather than relying on tests to catch it after the fact.
