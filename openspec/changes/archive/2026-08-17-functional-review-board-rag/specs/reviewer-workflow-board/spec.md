# Delta for Reviewer Workflow Board

## ADDED Requirements

### Requirement: Durable Review Board Cards

The system MUST expose a durable review-board read model for thesis reviewers, with each card carrying student identity, thesis title, priority, board state, review-run status, reviewer label when known, and Markdown report readiness.

#### Scenario: Board cards are returned from persisted documents and runs

- GIVEN thesis documents and review runs have been persisted
- WHEN a reviewer requests the review board
- THEN the API returns one card per relevant document/run projection
- AND every card includes `id`, `student_name`, `thesis_title`, `priority`, `board_state`, `review_run_status`, and `report_ready`

#### Scenario: Empty board is explicit

- GIVEN no thesis documents or review runs exist
- WHEN a reviewer requests the review board
- THEN the API returns an empty card list, not a fabricated sample board

### Requirement: Priority and Approval Workflow State

The system MUST persist reviewer workflow metadata separately from automated analysis status: priority can be `low`, `normal`, or `urgent`, and approval can only be set by an explicit reviewer action.

#### Scenario: Priority is updated without changing analysis status

- GIVEN a board card exists
- WHEN a reviewer changes priority to `urgent`
- THEN the card priority becomes `urgent`
- AND the underlying review-run lifecycle status is unchanged

#### Scenario: Approval is human-controlled

- GIVEN a review run has completed
- WHEN a reviewer approves the item
- THEN the board state becomes `approved`
- AND the transition is recorded as reviewer workflow metadata, not as automated analysis output

### Requirement: Board State Projection

The system MUST project board state from workflow metadata plus review-run lifecycle status without hiding failed or cancelled runs.

#### Scenario: Running lifecycle statuses appear In Review

- GIVEN a review run is `queued`, `extracting`, `segmenting`, `validating`, `rag_reviewing`, or `reporting`
- WHEN the board card is projected
- THEN `board_state` is `in_review`

#### Scenario: Completed unapproved runs appear Reviewed

- GIVEN a review run is `completed`
- AND the workflow item is not approved
- WHEN the board card is projected
- THEN `board_state` is `reviewed`

#### Scenario: Failed and cancelled runs remain visible

- GIVEN a review run is `failed` or `cancelled`
- WHEN the board card is projected
- THEN the card remains visible
- AND the response includes an attention field explaining the terminal status

### Requirement: Server-Side Thesis Upload Size Limit

The API MUST reject thesis upload files larger than 20 MB before persisting metadata, storing the file, or starting a review run.

#### Scenario: Oversized thesis upload is rejected server-side

- GIVEN a reviewer submits a PDF or DOCX larger than 20 MB
- WHEN the upload endpoint validates the file
- THEN the API returns a validation error
- AND no thesis document is persisted
- AND no review run is created

#### Scenario: Boundary size is accepted

- GIVEN a reviewer submits a PDF or DOCX whose size is exactly 20 MB
- WHEN the upload endpoint validates the file
- THEN size validation passes

### Requirement: Upload-To-Board Transition

The system MUST make a newly-started review visible as `in_review` in the board projection.

#### Scenario: Starting a review moves the card into In Review

- GIVEN a thesis document exists with no terminal approval
- WHEN a review run is started for that document
- THEN the board projection for that item is `in_review`
- AND the card includes the current review-run id

### Requirement: Normative Segment and Embedding Index

The system MUST persist normative source segments and embeddings so review runs can retrieve bounded normative context instead of only prompting over the full static corpus.

#### Scenario: Normative segments are seeded idempotently

- GIVEN normative source files exist
- WHEN the RAG foundation seed operation runs
- THEN durable `normative_segment` rows exist for source text chunks
- AND repeated seeding does not duplicate segment rows

#### Scenario: Normative embeddings are stored in pgvector

- GIVEN normative segments exist
- WHEN embeddings are generated by the configured embedding provider
- THEN vectors are persisted in pgvector-backed storage
- AND vectors remain linked to their originating normative segment

### Requirement: Similarity Retrieval and Fallback Honesty

The system MUST retrieve similar normative segments for thesis text when embeddings are available, and MUST fall back to CAG without claiming retrieved-context RAG when retrieval is unavailable.

#### Scenario: Similarity retrieval returns source references

- GIVEN persisted normative segment embeddings exist
- WHEN thesis text is embedded and queried
- THEN the retrieval result includes source references, segment text, and similarity scores

#### Scenario: Unavailable retrieval falls back without false RAG provenance

- GIVEN retrieval is unavailable or returns no context
- WHEN the review pipeline runs
- THEN the worker receives no retrieved-context payload
- AND persisted provenance does not claim retrieved-context RAG was used

### Requirement: Retrieved Context Review Provenance

The system MUST inject retrieved normative context into the worker review path and preserve provenance only when retrieved context was actually used.

#### Scenario: Retrieved context is injected into the review prompt

- GIVEN retrieved normative segments are available
- WHEN the API invokes the worker CAG review endpoint
- THEN the request includes `rag_context`
- AND the worker prompt uses retrieved normative context instead of the full static corpus

#### Scenario: Retrieval provenance is persisted with findings

- GIVEN retrieved normative context was used for a review
- WHEN a finding is persisted
- THEN finding metadata records that retrieved context was used
- AND the metadata includes traceable normative segment references

## MODIFIED Requirements

### Requirement: Functional Reviewer UX Shell

The reviewer UI MUST consume durable board data when the board API is available, while preserving the existing sample seam only as a non-production fallback/demo state.

#### Scenario: Board UI prefers API data

- GIVEN the board API returns cards
- WHEN the reviewer opens the board UI
- THEN the board renders API cards through the existing board view model
- AND it does not present sample cards as persisted records
