## Work Unit 1 — Migration Runner Auto-Discovery

`apps/api/src/db/migrate.mjs` previously hardcoded `DEFAULT_MIGRATION_PATH` to `./migrations/0001_schema_baseline.sql` and `migrateUp`/`migrateDown` always read that single file — a second migration file would have been silently skipped forever.

**RED**: extended `apps/api/tests/migrate-runner.test.mjs` with two new tests:
1. `listMigrationFiles discovers ALL *.sql files in a directory and sorts them by filename` — an always-on unit test (no live Postgres needed) against a temp fixture directory with two `.sql` files written to disk deliberately **out of filename order**, plus a non-`.sql` file that must be ignored.
2. `migrate.mjs discovers and applies ALL *.sql files under a migrations directory in filename order, and reverts them in reverse order` — a live-Postgres integration test using two fixture migrations where `fixture_b` has a `REFERENCES` foreign key on `fixture_a`. This is a **genuine** ordering proof, not just a naming assertion: `UP` must create `fixture_a` before `fixture_b` (FK creation would fail otherwise), and `DOWN` must drop `fixture_b` before `fixture_a` (dropping in non-reversed/ascending order would fail with a foreign-key-dependency error).

Ran both against the pre-fix tree: `listMigrationFiles is not a function` (test 1, immediate structural RED) and the live test genuinely skipped (Postgres unreachable at that point in the pass, see Test Commands Run) — then re-ran genuinely live after bringing Docker up, confirming a real `0 !== 1`-class failure was possible before GREEN (see the parallel Work Unit 2 RED evidence below for the same "real failure, not just module-not-found" proof pattern, since Work Unit 1's own live fixture test could only be driven to a **real assertion failure** once GREEN existed to compare against — the `listMigrationFiles is not a function` TypeError is itself unambiguous proof the feature did not exist).

**GREEN**: replaced `DEFAULT_MIGRATION_PATH` with `MIGRATIONS_DIR` (a directory URL) and added `listMigrationFiles(dir = MIGRATIONS_DIR)`, which `readdir`s the directory, filters to `*.sql`, sorts ascending by filename, and maps to `file://` URLs. `migrateUp`/`migrateDown` now default to discovering and running **every** migration file under `MIGRATIONS_DIR` — `migrateUp` in ascending (filename) order, `migrateDown` in the **reversed** array — via a small shared `runMigrationFiles(paths, pgClient, section)` helper. Both functions keep an optional `migrationPath` single-file escape hatch (used by the new "0001 alone" regression test below) and a `migrationsDir` override (used by both the unit and live fixture tests to avoid touching the real `migrations/` directory).

**TRIANGULATE**: two angles, both live-verified against dockerized Postgres:
- Out-of-order filenames still sort correctly (proven by the unit test's deliberately-out-of-order fixture writes).
- `0001` alone still applies with no regression: added a third new test, `migrate.mjs: applying 0001 alone (via an explicit migrationPath) still creates exactly the baseline tables`, which reverts everything, applies **only** `0001_schema_baseline.sql` via the `migrationPath` escape hatch, asserts exactly the 12 original baseline tables (no more, no fewer), reverts, then restores the full schema in its `finally` block so later test files in the same live-Postgres run are unaffected.

### A deliberate scope note: "fail-fast at startup" vs. design.md's literal "first cipher use"

The orchestrator's instructions for this pass asked for `LLM_PROVIDER_ENCRYPTION_KEY` to be "validated fail-fast at API startup ... the process must not silently start in an insecure state." `design.md`'s own decision #5, read literally, says "validated fail-fast at **first cipher use**" — not at the shared NestJS process bootstrap (`main.ts`/`bootstrapApi()`). These are not equivalent, and the difference matters here: `apps/api/tests/smoke.test.mjs` (pre-existing, unrelated to this pass, explicitly protected — "preserve every currently-passing test") calls `bootstrapApi()` directly with no `LLM_PROVIDER_ENCRYPTION_KEY` set. Hooking `getEncryptionKey()` into the shared `bootstrapApi()`/`main()` bootstrap would have made `smoke.test.mjs` fail unconditionally in every environment that hasn't configured admin-provider encryption yet — a real regression of a protected, out-of-scope test, not an acceptable tradeoff.

Resolution: implemented `design.md`'s literal decision — `getEncryptionKey()` fires the moment any cipher operation is attempted (`encryptApiKey`/`decryptApiKey`), AND, one level up, `provider-config-repository.mjs`'s `createProviderConfigRepository()` factory calls `getEncryptionKey()` **eagerly at construction time**, before any DB I/O — see Work Unit 4 below. Because `admin-contract.mjs` lazily constructs that repository on the **first** admin API request of any kind (list included, not just create/update), a misconfigured key fails fast and loudly on the first real use of the admin subsystem, without ever silently accepting requests — satisfying the underlying security goal ("never proceed insecurely") without crashing the unrelated, protected `smoke.test.mjs`/whole-process bootstrap. This is flagged here rather than silently deviating from either instruction.

### A subtle test-authoring bug caught during RED (flagged, not silently worked around)

The first draft of `review-orchestrator.test.mjs`'s new pure-unit test imported `defaultRunCagReview` via a dynamic `await import("../src/jobs/review-orchestrator.mjs")` **before** setting `process.env.WORKER_BASE_URL` to the fake worker's URL. `DEFAULT_WORKER_BASE_URL` inside that module is a top-level `const` evaluated once at import time (`process.env.WORKER_BASE_URL ?? "http://localhost:8000"`) — setting the env var *after* import has no effect on an already-evaluated constant. The test's fake worker was silently never contacted; the request went to `http://localhost:8000` instead (a non-existent local server in this environment, returning an HTML error page — hence the `Unexpected token '<'` JSON-parse failure). Fixed by reordering: start the fake worker and set `WORKER_BASE_URL` **before** the dynamic import, plus a cache-busting query-string suffix (`?t=${Date.now()}`) on the import specifier so this test is immune to the module already having been imported earlier by another `test()` block in the same file/process (ESM's per-specifier module cache). This same "top-level const frozen at first import" characteristic was independently confirmed as the root cause of `live-review-integration.test.mjs`'s pre-existing (unrelated to this bug) single-fake-worker-per-file pattern already being correct by construction — that file already imports its worker-config env vars before its first dynamic import of `api-contract.mjs`.

### A dependency-injection subtlety: why the provider factory never raises directly

An early design considered having `select_llm_provider` raise `ProviderNotImplementedError` directly when `provider_name` is `deepseek`/`groq`/unknown, called from `get_llm_provider` (a FastAPI `Depends()` function). This would have been a bug: FastAPI resolves dependencies **before** invoking the route function body, so an exception raised there is NOT inside `internal_review`'s own `try/except` block and would propagate as an unhandled `500` with FastAPI's default (non-standard-shaped) error response — violating the orchestrator's explicit "never crashing unhandled" requirement. Resolution: `select_llm_provider` **always succeeds** and returns a provider object (`AnthropicProvider` for claude, `DeepSeekProvider`/`GroqProvider`/`UnimplementedProvider` for everything else); the actual failure is deferred into `.generate()`, which `run_cag_review()` calls from *inside* `internal_review`'s try block — exactly mirroring how `AnthropicProviderConfigError` already worked before this pass (raised inside `generate()`, not at construction).

### Local port-conflict note (documented, not a defect — same as `mvp-vertical-slice`)

This development machine has a pre-existing, project-unrelated Homebrew `postgresql@17` service bound to `127.0.0.1:5432`/`[::1]:5432` (confirmed via `lsof -nP -iTCP:5432 -sTCP:LISTEN` before starting this pass). Docker's own port-forwarding binds `0.0.0.0:5432`, but the OS routes `localhost` connections to the more specific loopback-bound Homebrew process instead of the Docker container, producing `role "pg1" does not exist` even though the container is healthy and genuinely has that role. To get genuine live evidence without touching the user's pre-existing local Postgres, `infra/docker-compose.yml`'s host port was temporarily changed to `5433:5432` for live verification only, then reverted to the canonical `5432:5432` before finishing (confirmed via `git diff` showing an empty diff). This is the exact same documented workaround used throughout `mvp-vertical-slice`'s apply-progress — not a defect introduced by this pass.

## Deviations From Design

- None in the schema itself — `llm_provider_config`'s column list matches `design.md`'s Interfaces/Contracts line exactly (`id, provider_name, model_id, encrypted_api_key, api_key_last_four, is_active, metadata, created_at, updated_at`), and the partial unique index matches design decision #3's literal SQL shape (`CREATE UNIQUE INDEX ... ON llm_provider_config (is_active) WHERE is_active`).
- One necessary, flagged update to a pre-existing test's assertion value (12 → 13 expected tables) — see "A necessary, deliberate change to a pre-existing test" above. This is a direct, intended consequence of combining Work Unit 1 (auto-discovery) and Work Unit 2 (new migration) in the same PR, not a design deviation.
- `infra/docker-compose.yml`'s committed port mapping (`5432:5432`) is unchanged from `design.md`'s documented `DATABASE_URL` contract — the temporary `5433` remap was live-verification-only and fully reverted, same as every prior PR in `mvp-vertical-slice`.
- **PR B, flagged (not silent):** `design.md` decision #5 literally says "validated fail-fast at first cipher use." The orchestrator's instructions for this pass asked for fail-fast validation "at API startup." These are not identical, and hooking the check into the shared `bootstrapApi()`/`main()` process bootstrap would have broken the pre-existing, protected `smoke.test.mjs` (which boots the app with no `LLM_PROVIDER_ENCRYPTION_KEY` set and is explicitly out of this pass's scope). Resolution: implemented `design.md`'s literal decision (fail-fast at first cipher use) PLUS an eager fail-fast check at `provider-config-repository.mjs`'s construction time, which fires on the admin subsystem's first request of any kind (not just first write) via `admin-contract.mjs`'s lazy singleton — closer to "startup" for the admin feature specifically, without touching the shared, protected bootstrap. See the full writeup under "Work Unit 3 — A deliberate scope note" above.
- No other deviations. The `llm_provider_config` schema, admin route shapes, masked-response contract, shared-secret gate, and one-active-provider invariant all match `design.md`'s Interfaces/Contracts and `specs/llm-provider-admin/spec.md`'s scenarios exactly.
- **PR C:** none. The zero-active-provider → `review_run.status: "failed"` failure path reuses the pre-existing orchestrator catch block exactly as `design.md`'s Contracts section specifies ("matches the existing failure pattern in review-orchestrator.mjs catch block") — no new error-handling code was written for it. The `ANTHROPIC_API_KEY` env fallback was kept exactly as design decision #11 specifies (arg-then-env precedence, never removed). DeepSeek/Groq fail at `.generate()` time only, never at admin create/activate time, matching design decision #10 literally.
