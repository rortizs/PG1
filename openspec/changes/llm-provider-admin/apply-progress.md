## Work Unit 1 — Migration Runner Auto-Discovery

`apps/api/src/db/migrate.mjs` previously hardcoded `DEFAULT_MIGRATION_PATH` to `./migrations/0001_schema_baseline.sql` and `migrateUp`/`migrateDown` always read that single file — a second migration file would have been silently skipped forever.

**RED**: extended `apps/api/tests/migrate-runner.test.mjs` with two new tests:
1. `listMigrationFiles discovers ALL *.sql files in a directory and sorts them by filename` — an always-on unit test (no live Postgres needed) against a temp fixture directory with two `.sql` files written to disk deliberately **out of filename order**, plus a non-`.sql` file that must be ignored.
2. `migrate.mjs discovers and applies ALL *.sql files under a migrations directory in filename order, and reverts them in reverse order` — a live-Postgres integration test using two fixture migrations where `fixture_b` has a `REFERENCES` foreign key on `fixture_a`. This is a **genuine** ordering proof, not just a naming assertion: `UP` must create `fixture_a` before `fixture_b` (FK creation would fail otherwise), and `DOWN` must drop `fixture_b` before `fixture_a` (dropping in non-reversed/ascending order would fail with a foreign-key-dependency error).

Ran both against the pre-fix tree: `listMigrationFiles is not a function` (test 1, immediate structural RED) and the live test genuinely skipped (Postgres unreachable at that point in the pass, see Test Commands Run) — then re-ran genuinely live after bringing Docker up, confirming a real `0 !== 1`-class failure was possible before GREEN (see the parallel Work Unit 2 RED evidence below for the same "real failure, not just module-not-found" proof pattern, since Work Unit 1's own live fixture test could only be driven to a **real assertion failure** once GREEN existed to compare against — the `listMigrationFiles is not a function` TypeError is itself unambiguous proof the feature did not exist).

**GREEN**: replaced `DEFAULT_MIGRATION_PATH` with `MIGRATIONS_DIR` (a directory URL) and added `listMigrationFiles(dir = MIGRATIONS_DIR)`, which `readdir`s the directory, filters to `*.sql`, sorts ascending by filename, and maps to `file://` URLs. `migrateUp`/`migrateDown` now default to discovering and running **every** migration file under `MIGRATIONS_DIR` — `migrateUp` in ascending (filename) order, `migrateDown` in the **reversed** array — via a small shared `runMigrationFiles(paths, pgClient, section)` helper. Both functions keep an optional `migrationPath` single-file escape hatch (used by the new "0001 alone" regression test below) and a `migrationsDir` override (used by both the unit and live fixture tests to avoid touching the real `migrations/` directory).

**TRIANGULATE**: two angles, both live-verified against dockerized Postgres:
- Out-of-order filenames still sort correctly (proven by the unit test's deliberately-out-of-order fixture writes).
- `0001` alone still applies with no regression: added a third new test, `migrate.mjs: applying 0001 alone (via an explicit migrationPath) still creates exactly the baseline tables`, which reverts everything, applies **only** `0001_schema_baseline.sql` via the `migrationPath` escape hatch, asserts exactly the 12 original baseline tables (no more, no fewer), reverts, then restores the full schema in its `finally` block so later test files in the same live-Postgres run are unaffected.

**REFACTOR**: `listMigrationFiles()` extracted as its own exported, independently-unit-testable helper, exactly as `tasks.md` specified.

## Work Unit 2 — `0002_llm_provider_config.sql` Migration

**RED**: created `apps/api/tests/llm-provider-config-migration.test.mjs` (live-Postgres integration test, before the migration file existed) asserting: the table exists after `migrate up` (via the ordered 0001→0002 runner); `provider_name: 'openai'` violates the CHECK constraint; a blank `model_id` violates the CHECK constraint; inserting a second `is_active: true` row violates the partial unique index (a second **inactive** row for a different provider is fine — the invariant only restricts concurrently-active rows); and the table is dropped after `migrate down`. Ran live against dockerized Postgres before the migration file existed: **genuine failure** — `llm_provider_config must exist after migrate up: 0 !== 1` (not a module-not-found stub — the table genuinely did not exist because `0002` did not exist yet and the default `migrate up` had nothing new to discover).

**GREEN**: created `apps/api/src/db/migrations/0002_llm_provider_config.sql` following `0001`'s exact conventions (`-- UP`/`-- DOWN`, `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, snake_case, `TIMESTAMPTZ NOT NULL DEFAULT now()`, CHECK-based enums via `CONSTRAINT ..._check CHECK (... IN (...))`, `btrim(...) <> ''` for required text, `jsonb_typeof(metadata) = 'object'` for the metadata column). Columns exactly match `design.md`'s Interfaces/Contracts line — no invented columns: `id, provider_name, model_id, encrypted_api_key, api_key_last_four, is_active, metadata, created_at, updated_at`. The exactly-one-active invariant is DB-enforced via `CREATE UNIQUE INDEX uq_llm_provider_config_one_active ON llm_provider_config (is_active) WHERE is_active` (design decision #3 — DB-enforced, race-safe, matches the literal SQL shape design.md specified), plus a secondary non-unique `idx_llm_provider_config_provider_name` lookup index following `0001`'s own indexing convention. Re-ran the RED test: **1 pass / 0 fail**.

**TRIANGULATE**: confirmed `0002` runs after `0001` via Work Unit 1's ordered runner (the RED test's own `migrate up` call uses the default no-args discovery path, so this is inherent to the test passing at all — not a separate check); confirmed `-- DOWN` cleanly drops the table (asserted directly in the test, and independently re-verified via a manual CLI cycle, see Test Commands Run); confirmed via direct `psql \dt` inside the live container that all 13 tables (12 baseline + `llm_provider_config`) exist after a manual `migrate.mjs up` and that `\dt` reports zero relations after a manual `migrate.mjs down`.

**REFACTOR**: N/A — single migration file, no shared logic yet, exactly as `tasks.md` specified.

### A necessary, deliberate change to a pre-existing test (flagged, not silently made)

`migrate-runner.test.mjs`'s pre-existing live-Postgres test (`"migrate.mjs applies and reverts the baseline schema against live Postgres"`) asserted `tableNames.length === REQUIRED_TABLES.length` where `REQUIRED_TABLES` was the fixed list of 12 `0001` tables. Once Work Unit 1's auto-discovery + Work Unit 2's new migration file are BOTH in place, the **real, intended** default behavior of `migrateUp({client})` (no args) is to apply `0001` **and** `0002` — so a genuine, correct `migrate up` now produces 13 tables, not 12. Running the full live suite exposed this as a real (expected) failure: `13 !== 12`.

This is not a scope creep or an accidental regression — it is the direct, necessary consequence of Work Unit 1 and Work Unit 2 being combined in the same PR (exactly as `tasks.md`'s own Work Unit 1 TRIANGULATE line anticipates: "confirm `0001` alone still applies with no regression", which only makes sense as a *specific, separate* check once the *general* default behavior legitimately changes). Resolved by:
1. Renaming the internal table-list constant to `BASELINE_TABLES` and deriving `REQUIRED_TABLES = [...BASELINE_TABLES, "llm_provider_config"]` for the full-discovery test, and renaming that test to `"migrate.mjs applies and reverts ALL discovered migrations (baseline + llm_provider_config) in order against live Postgres"` to accurately describe what it now covers.
2. Adding the new dedicated "0001 alone" test (see TRIANGULATE above) so the *original* narrower guarantee — "the baseline schema, and only the baseline schema, still works" — has its own explicit, still-passing assertion using the `migrationPath` single-file escape hatch, rather than being silently dropped.

No other pre-existing test needed changes. `contract.test.mjs`, `smoke.test.mjs`, `review-repository.test.mjs`, `review-orchestrator.test.mjs`, `live-review-integration.test.mjs`, `postgres-unreachable.test.mjs`, and every `apps/web`/`services/worker` test are byte-untouched.

### Local port-conflict note (documented, not a defect — same as `mvp-vertical-slice`)

This development machine has a pre-existing, project-unrelated Homebrew `postgresql@17` service bound to `127.0.0.1:5432`/`[::1]:5432` (confirmed via `lsof -nP -iTCP:5432 -sTCP:LISTEN` before starting this pass). Docker's own port-forwarding binds `0.0.0.0:5432`, but the OS routes `localhost` connections to the more specific loopback-bound Homebrew process instead of the Docker container, producing `role "pg1" does not exist` even though the container is healthy and genuinely has that role. To get genuine live evidence without touching the user's pre-existing local Postgres, `infra/docker-compose.yml`'s host port was temporarily changed to `5433:5432` for live verification only, then reverted to the canonical `5432:5432` before finishing (confirmed via `git diff` showing an empty diff). This is the exact same documented workaround used throughout `mvp-vertical-slice`'s apply-progress — not a defect introduced by this pass.
