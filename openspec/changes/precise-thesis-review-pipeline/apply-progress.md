## Deviations From Design (PR1)

- **`ExtractedSection.parent_index` (index-based) instead of a literal `parent_section_id` field.** `design.md` D2's mapping paragraph says section detection produces "`parent_section_id` via the level stack" — read literally as a Python dataclass field name, this is impossible: no real database id exists yet at extraction time (ids are only assigned once `insertDocumentSections` runs, on the Node side). Design's own D3 contract for `insertDocumentSections` confirms the intended shape is index-based (`sections[] ... { index, parentIndex|null, ... }`, resolved against `idByIndex` "safely because a parent heading ALWAYS precedes its child in document order"). So D2's `parent_section_id` wording describes the eventual DB **column** the level-stack value maps to, not a literal Python field name — implemented as `ExtractedSection.parent_index: int | None`, matching D3's own `parentIndex` contract exactly, and documented with an explicit docstring on the dataclass explaining why. This is an implementation-necessary interpretation, not a behavioral deviation — the end result (a real `document_section.parent_section_id` FK, correctly resolved) is exactly what D2/D3 together specify.
- **`documentSectionId` resolved by page-range containment, not `f.section_index`.** Design.md D3's literal wiring formula is `documentPageId/documentSectionId ... from idByPageNumber[f.page_number] and idByIndex[f.section_index]` — but `f.section_index` is a field on the **chunked** review response contract (design.md's Interfaces/Contracts `/internal/review` response, `{"findings": [{..., "section_index": 0}]}`), which is PR5's scope (Work Unit 8), not PR1's. ## Deviations From Design (PR2)

- **Scenario 3 of `live-review-integration.test.mjs` was deliberately reworked, not just extended.** Before this pass, breaking only `/internal/review` (`worker.setNextReview(500, ...)`) made the whole run `status: 'failed'`, because there was no second, independent path. With Work Unit 5's design.md D9 isolation now in place, the deterministic rules path (defaulting to `{findings: []}` in the fake worker) genuinely *succeeds* even when LLM review is broken — so under the new, correct architecture that same setup now yields `status: 'completed'` with `metadata.partial_failure.llm` (exactly what design.md D3's semantics require, and exactly what the new "Scenario 4" proves directly). Scenario 3's *original intent* — "the worker is genuinely broken → the run fails" — was preserved by also breaking `/internal/rules` (`worker.setNextRules(500, ...)`), so both independent paths fail and the assertion `status === 'failed'` stays true, unchanged. This is not a silent test loosening: the change is the direct, necessary consequence of design.md's own stated isolation requirement, documented here exactly as `mvp-vertical-slice`/`llm-provider-admin`'s prior "Deliberate test rework" sections did.
- **`rapidfuzz` was intentionally NOT added to `pyproject.toml` this pass**, even though design.md's File Changes table lists `pysbd>=0.3.4, pyspellchecker>=0.8, rapidfuzz>=3.9` together on one row for `services/worker/pyproject.toml`. Reading design.md D4 (`GROUNDING_FUZZ_MIN`/`DEDUP_MIN`, both `rapidfuzz.fuzz.*`) shows `rapidfuzz` is needed only by the chunked LLM review loop's grounding/dedup logic — PR5's scope (Work Unit 8), not PR2's deterministic rules. The task prompt's own constraint ("New Python dependencies (`pysbd`, `pyspellchecker`) need explicit addition") independently confirms this scoping. Adding an unused dependency now would be scope creep against Work Units 4–5; it is deferred to the PR5 apply pass, flagged here rather than silently added or silently skipped without explanation.
- **`pyspellchecker`'s bundled Spanish dictionary has real coverage gaps for common inflected verb forms** — the live `curl` proof above genuinely flagged the correctly-spelled word "funciona" (a standard conjugation of "funcionar") as a spelling miss, alongside the two intentionally-misspelled tokens in the fixture. This is not a bug in this pass's implementation of the conservatism gate (every one of the 6 documented conditions — lowercase, len≥4, not-acronym, no-digit, not-in-citation-span, dictionary-miss — is applied correctly and is unit-tested); it is an inherent limitation of `pyspellchecker`'s frequency-based dictionary, which design.md chose specifically to avoid a heavier NLP dependency (the same tradeoff already accepted for `pysbd` over spaCy). Documented here as a known false-positive risk for future review — not silently hidden, and not a scope violation, since the spec's literal requirement ("check extracted text against a Spanish dictionary and flag words not recognized") is satisfied exactly as specified.
